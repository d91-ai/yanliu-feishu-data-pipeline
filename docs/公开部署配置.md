# 公开部署配置

本文只使用部署者自己的飞书资源。不要把 `.env`、字段绑定、访问令牌、日志或会议材料提交到 Git。

## 1. 创建资源

1. 创建飞书自建应用并启用长连接事件接收。
2. 按 `.implementation/meeting-pipeline-contract/contract/unified-base.schema.json` 创建 Base 字段和四个审核视图。
3. 为三个审核字段配置 `未审核`、`已审核`、`需重审` 三个选项。
4. 新增附件字段 `会议纪要上传附件`。
5. 创建源纪要、审核前、审核后、历史版本及两类观点 Markdown/JSON 的 Drive 目录，并把自建应用加入协作者。
6. 在开放平台选择“长连接”订阅方式，并添加以下两个应用级事件：
   - `drive.file.bitable_record_changed_v1`（多维表格记录变更）；
   - `drive.file.created_in_folder_v1`（文件夹下文件已创建）。
7. 按开放平台提示开通上述事件所需的 Base、Drive 与事件订阅权限，创建并发布新的应用版本，再把应用安装到部署者自己的企业。只执行后文的资源级 `subscribe-router` 不能替代这一步；应用版本未发布时，新事件配置不会在线上生效。

运行链路至少需要以下应用身份权限：`base:field:read`、`base:record:read`、`base:record:create`、`base:record:update`、`drive:drive`。创建资源级事件订阅的所有者账号还需在授权页确认 `drive:drive`、`docs:doc`、`sheets:spreadsheet`、`docs:event:subscribe`。飞书后台若显示更细粒度的同义权限，以当前后台提示为准；出现 403 时不要反复重试写入，应先核对权限、版本发布、企业安装和资源协作者范围。

飞书 CLI 在本项目中用于 Base/Workflow 的读取、创建和核对；Router 的常驻事件连接使用飞书官方 Python SDK，不依赖 CLI 常驻运行。可先执行 `lark-cli --help` 确认可用，再阅读 `.implementation/meeting-pipeline-ops/apply_unified_base.py` 和 `.implementation/meeting-pipeline-ops/provision_collaboration_workflows.py` 的 dry-run 参数。不要在未核对计划时使用写入参数。

## 2. 配置 Router

从仓库根目录执行：

```bash
cd .implementation/version-retention/feishu-drive-to-bitable
cp .env.router.example .env.router
cp .env.meeting-minutes.example .env.meeting-minutes
cp .field-bindings.meeting-minutes.example.json .field-bindings.meeting-minutes.json
```

填写部署者自己的 App ID、App Secret、Base token、table ID、Drive folder token 和字段 ID。`MEETING_MINUTES_SKILL_HOST_DIR` 使用仓库内 `.implementation/investment-meeting-minutes` 的绝对路径。

统一模式至少确认：

```text
FEISHU_PIPELINE_MODE=unified
FEISHU_FORM_INGRESS_ENABLED=true
FEISHU_ARCHIVE_HTTP_ENABLED=false
```

计算容器内会议纪要校验脚本所需哈希：

```bash
sha256sum ../../../.implementation/investment-meeting-minutes/scripts/validate_meeting_minutes_contract.py
```

将结果写入 `FEISHU_MEETING_CONTRACT_VALIDATOR_SHA256`。首次检查保留 `FEISHU_DRY_RUN=true`；完成只读检查并准备执行真实写入时，再显式改为 `false`。

## 3. 配置 Worker

```bash
cd "$(git rev-parse --show-toplevel)/.implementation/meeting-pipeline-worker"
cp .env.example .env.worker.source
```

在 `.env.worker.source` 中填写部署者自己的飞书资源和 Drive 目录。随后由仓库脚本填入已公开的 Skill 路径、共享队列路径和所有运行树 SHA256：

```bash
python3 -B ../meeting-pipeline-ops/prepare_public_worker_env.py \
  --source-env .env.worker.source \
  --target-env .env.worker.disabled \
  --apply
python3 -B unified_worker_service.py --env-file .env.worker.disabled check
```

公开标的观点 Skill 附带空的证券主数据表头，因此不会泄露任何证券主数据。需要名称与代码自动校对时，在部署前用部署者自己的 UTF-8 CSV 替换其 `data/security_master.csv`，列为 `target_name,stock_code,market,aliases`，然后重新运行环境准备脚本计算哈希。

长纪要处理建议保持以下默认值；若模型或机器较慢，可继续增大超时，但不要把失败任务误判为成功：

```text
FEISHU_PIPELINE_MODEL_REASONING_EFFORT=medium
FEISHU_PIPELINE_MODEL_TIMEOUT_SECONDS=1800
```

## 4. 订阅并启动

先确认开放平台中的两个应用级事件已经添加并随应用版本发布，再让 Router 创建具体 Drive 文件夹和 Base 的资源级事件订阅：

```bash
cd "$(git rev-parse --show-toplevel)/.implementation/version-retention/feishu-drive-to-bitable"
docker compose --env-file .env.router run --rm \
  feishu-drive-to-bitable-router \
  python feishu_drive_to_bitable.py subscribe-router --apply
```

启动 Router：

```bash
docker compose --env-file .env.router config --quiet
docker compose --env-file .env.router up -d --build
docker compose --env-file .env.router logs --tail=100 feishu-drive-to-bitable-router
```

日志中应出现 Router 已加载路由并启动长连接。若上传附件后没有生成任务，优先检查：应用版本是否已发布、上述两个应用级事件是否存在、`FEISHU_FORM_INGRESS_ENABLED=true`、`FEISHU_DRY_RUN=false`，以及 Router 与 Worker 是否指向同一组 generation/receipt 目录。

启用并启动 Worker：

```bash
cd "$(git rev-parse --show-toplevel)/.implementation/meeting-pipeline-worker"
python3 -B ../meeting-pipeline-ops/create_enabled_worker_env.py \
  --source-env .env.worker.disabled \
  --target-env .env.worker.enabled \
  --apply
python3 -B unified_worker_service.py --env-file .env.worker.enabled check
python3 -B unified_worker_service.py --env-file .env.worker.enabled serve --apply
```

生产环境应使用 systemd 或等价服务管理器托管 Worker，并持久化 Router 的 `data` 目录和 Worker 的工作目录。

## 5. 创建并启用五个协作 Workflow

先在未跟踪的 `.env.meeting-minutes` 中填写 `FEISHU_WORKFLOW_REVIEWER_OPEN_ID` 和可选的 `FEISHU_WORKFLOW_REVIEWER_NAME`。只读查看计划：

```bash
cd "$(git rev-parse --show-toplevel)/.implementation/meeting-pipeline-ops"
python3 -B provision_collaboration_workflows.py \
  --env-file ../version-retention/feishu-drive-to-bitable/.env.meeting-minutes
```

核对输出恰好包含五条 Workflow 后，增加 `--apply` 创建并启用。脚本会校验所需字段；同名 Workflow 已存在但未启用时只执行启用，不会调用 AI。若改用飞书页面手工搭建，必须对每一条规则分别点击“保存并启用”，然后回到 Workflow 列表确认五条状态均为“已启用”。详细条件见 [`多维表格Workflow搭建.md`](多维表格Workflow搭建.md)。仓库中的旧版 `create_structured_generation_workflow.py` 不属于当前五条通知型 Workflow，不要用于本步骤。

## 6. 配置重启恢复和漏事件补偿

复制 `.implementation/meeting-pipeline-ops/deployment/` 中的三个 systemd 模板，替换绝对路径和运行用户后执行 `systemctl enable --now`。Windows + WSL2 还需在任务计划程序中让登录动作启动对应 WSL 发行版，示例见同目录的 `start-wsl-pipeline.ps1.example`。

补偿器会扫描最近 48 小时内“附件已存在但会议ID仍为空”的记录。首次启用前先运行只读扫描：

```bash
cd "$(git rev-parse --show-toplevel)/.implementation/meeting-pipeline-ops"
python3 -B reconcile_missed_ingress.py \
  --router-env ../version-retention/feishu-drive-to-bitable/.env.router \
  --route-env ../version-retention/feishu-drive-to-bitable/.env.meeting-minutes \
  --once
```

候选数量合理后再加 `--apply`，或启用已含 `--apply` 的 reconciler 服务模板。服务启动后确认 Router、Worker、Reconciler 均为 active；重启机器后还必须再次检查。
