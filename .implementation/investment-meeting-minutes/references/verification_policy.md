# 核验与标的归因规则

本文件合并名称校对、股票代码来源、证据边界和标的归因规则。外部资料只能用于确认名称、代码、术语、公开客户/供应商、事件或数字口径，不得补写会议没有出现的新结论。

## 证据层级

### source_evidence

来源包括原始音频、SenseVoice 转写、带时间戳转写 JSON、用户上传文档、人工初审稿和同会话补充说明。

地位：
- 是会议内容最高优先级证据。
- 只能据此整理会议中实际说过的判断、数字、动作和不确定表达。
- 外部资料不能替代 source evidence 编造会议结论。
- 同会话内用户对公司名、股票代码、术语、候选项或事实边界的明确纠正/确认，属于高优先级人工修正，可用于更新 `doubtful_items` 和最终处理。若用户修正与原始音频/文稿或可靠公开事实冲突，不要静默覆盖；记录冲突并保留为存疑。

混合来源优先级：
- `audio_plus_document` 中，先完成音频转录，再比较原始音频/`aligned_transcript` 与用户上传文档、原始文本、人工初审稿、同会话补充说明的质量。
- 质量判断看覆盖完整度、发言顺序、逐字性、可靠时间戳、ASR 噪声、遗漏、人工校正痕迹和与其他同会话材料的一致性；选择质量较高的一侧作为正文主源。
- 未选为主源的一侧用于交叉对比：确认发言人、纠正明显错听、补充疑似遗漏、暴露音频/文档冲突，并为联网核验提供候选线索。
- 文档不得因为更顺或更像纪要就默认替代更可靠的音频证据；音频也不得在转写噪声重、漏段明显或同会话人工校正文稿质量更高时强行作为正文主源。若二者不一致，保留证据更清楚的一侧；无法判断的冲突进入 process notes 或 `doubtful_items`。
- 联网核验和 `a-stock-data` 只确认名称、代码、术语、公开事实或候选解释，不补写音频/文本都没有出现的会议内容。

### local_reference_evidence

来源包括 `query_symbol_candidates.py`、本地 A/HK/US 代码表、公司别名表、本地术语表或历史归档中可用的候选信息。

地位：
- 只用于候选纠错和缩小检索范围。
- 本地候选不是最终确认。
- 只有本地候选、外部尚未确认时，不得标记 `confirmed`。
- 置信不足、候选冲突或资源过期时必须保留为存疑或继续外部核验。

### external_verification_path

来源包括公司公告、交易所披露、CNINFO、公司官网、监管/协会资料、行业报告、可靠财经新闻和 `a-stock-data` live/network data。

地位：
- 辅助确认实体、代码、术语、客户公开信息、订单/产能/价格口径。
- 与 source evidence 冲突时，保留原始表述并列为存疑。
- 外部查询只发送候选实体、ticker、术语和必要公开事实关键词；不得发送原始长段落、发言人身份、私有链接、未公开客户/订单上下文或其他机密会议内容。无法在不暴露私有上下文的情况下确认时，保留为存疑或请求用户窄口径确认。

## 名称和代码核验

本地资源目录：

`$INVESTMENT_MINUTES_WORKSPACE/03 Resources`

常用路径：
- `market-symbols/a_share_list.csv`
- `market-symbols/global-stock-symbols-source/`
- `market-symbols/README.md`

查找顺序：
1. `a-stock-data` live sources when available.
2. Local A-share table.
3. Local global-symbol table for HK/US/other markets.
4. Official exchange, company announcement, company website, or other professional source when local candidates are insufficient.

规则：
- 不要把未确认 ticker 写成确定标题代码。
- 本地 symbol candidates 在多候选匹配时不是最终证据。
- 不局限于 A 股；HK/US/ADR/TW/其他上市证券作为会议标的、客户、供应商、竞争对手或重要可比对象出现时也要核验。
- 市场后缀保持一致：A 股优先 `.SZ`、`.SH`、`.BJ`；港股 `.HK`；美股使用本地/global symbol table 中的交易所 ticker。
- 当存疑口播名称有可编码候选时，最终纪要可把候选写成加粗存疑形式，例如 `**候选公司(99998.HK)**`，同时保留存疑表人工确认入口。

## 高风险 claim

以下信息写入终稿前必须核验：
- 公司名和股票代码
- 客户名、供应商名、竞争对手名
- 订单、产能、价格、收入、利润、毛利率、估值、市值
- 时间节点、政策事件、公告事件
- 产品型号、技术路线、专业术语
- 投资动作不是外部公开事实：买入、卖出、加仓、减仓、重点跟踪等动作必须逐项回到当前会话原文，核对动作主体、标的、方向、限定词和原句措辞；不得因外部资料无法证明个人动作而删改原文。动作中包含的公司名、代码或公开事件仍按上列规则做外部核验。

`candidate_only` / `unverified` / `not_found` 的 ticker 不得进入标题或标的行。若候选项能够匹配到明确证券代码，只能在正文中加粗保留候选名称和代码，同时在存疑表中保留人工确认入口；只有名称和代码均已确认、来自当前会议材料且语义上属于该段明确看好标的时，才可进入标题。

## 存疑处理

先建立一份内部 `doubtful_items` 清单，再从同一清单派生终稿表格和 verification sidecar。不要让 sidecar 变成第二套独立判断。

每条 `doubtful_items` 必须包含：
- `原始表述`：ASR、文稿或用户材料中的原始存疑词句。
- `存疑类型`：只能使用 `人名`、`说话人身份`、`公司或证券标的`、`行业术语`、`数字或时间`、`其他业务事实`。
- `当前判断`：写入终稿表格。
- `候选项`：候选为证券标的且能匹配代码时，写标准名称和代码。
- `是否需要 sidecar`：纯人名或纯说话人身份不确定为 `false`；公司或证券标的、行业术语、数字或时间、其他业务事实为 `true`。
- `上下文依据`：记录相关原文段落、语义位置、发言人/版块或时间戳线索。
- `检索/证据路径`：记录本地候选、a-stock-data、公告、交易所、官网、行业资料或其他可靠资料路径。
- `最终处理`：记录写入正文、正文加粗标注并入存疑表、不写入正式标的等处理。

`身份`、`嘉宾`、`发言人` 等词只在该行确实是纯人名或纯说话人身份不确定时，才按人名类处理。若疑点实际指向公司、证券标的、行业术语、数字、时间或其他业务事实，仍按对应业务类型进入核验流程。

不得只写 `待确认`、`需核实`、`未查到`、`听不清`；这些词不能替代当前判断和候选项。
需要审计时，只把 `是否需要 sidecar=true` 的同一批 `doubtful_items` 派生到终稿同 stem 的 `.verification.json` 或 `.verification.jsonl`。核验依据不写入最终 `## 二、存疑与待确认` 表格。

交付前做一次人工式自检：
- sidecar 中每条记录都能回到终稿的一条非人名存疑行。
- 同一条的 `原始表述`、`当前判断`、`候选项`、`最终处理` 在终稿表格和 sidecar 中不互相冲突。
- 如果冲突，回到 `doubtful_items` 统一修正并重新派生终稿表格和 sidecar，不通过新增 validator 硬规则解决。

当出现非人名存疑项时，主流程必须使用同一套核验 prompt：

```text
你是中文投研会议纪要的存疑项核验助手。请只核验当前会议材料中已经出现的非人名存疑项，不补写会议没有说过的新结论。

输入：
1. 会议上下文：相关原文段落、发言人/版块、时间戳或来源位置。
2. 存疑原始表述：ASR 或文稿中的原始词句。
3. 存疑类型：人名 / 说话人身份 / 公司或证券标的 / 行业术语 / 数字或时间 / 其他业务事实。
4. 候选解释：可能的人名、说话人身份、公司名、股票代码、简称、英文缩写、客户/供应商、数字、日期、产品、政策或事件。

核验要求：
1. 先用会议上下文判断候选是否语义匹配。
2. 再使用至少一种可靠证据路径核验：联网搜索到的可靠来源、a-stock-data、公司公告、官网、交易所/监管披露、研报/行业资料。本地代码表只作为候选线索，不能单独作为确认依据。
3. 本地候选和 ASR 输出只能作为线索，不能单独作为确认依据。
4. 外部资料只能用于确认名称、代码、术语、公开客户/供应商、事件或数字口径，不能补写会议没有出现的观点。
5. 外部查询只发送候选项和最小公开事实关键词，不发送原始会议长段、发言人身份、私有链接、未公开客户/订单上下文或机密 source text。
6. 如果证据冲突、证据不足、无法唯一确认，或必须暴露私有上下文才能确认，保留原始表述并进入存疑表。
7. `身份`、`嘉宾`、`发言人` 等词只在疑点确实是纯人名或纯说话人身份时按人名类处理；非人名业务疑点不得因此跳过核验。

输出每条 `doubtful_items`：
- 原始表述：
- 存疑类型：人名 / 说话人身份 / 公司或证券标的 / 行业术语 / 数字或时间 / 其他业务事实
- 当前判断：确认 / 保留原文 / 暂不采信 / 待人工确认
- 候选项：
- 是否需要 sidecar：true / false
- 上下文依据：
- 检索/证据路径：
- 最终处理：写入正文 / 正文加粗标注并入存疑表 / 不写入正式标的

注意：终稿 `## 二、存疑与待确认` 和 verification sidecar 都只从同一份 `doubtful_items` 派生；sidecar 记录核验过程，不二次改写判断。最终 Markdown 表格保留固定列，不加入详细核验依据。
```

## 校对规则

- 转录、校对、识别、联网核验、编辑、排版和验证不得静默跳过；某步骤不适用时记录 `skipped_reason`，失败时记录 failure reason、影响范围和最安全的下一步。
- 修正明显 ASR 错词，只允许删除无意义重复、ASR 噪声、纯口头填充词和重复起手式；必须保留发言人的原始判断、条件、语气、数字、时间、仓位动作、第一人称视角和不确定表达，不得借校对名义总结、改写或改变人称。
- 校对后的正文应能回到同一发言轮次的原始音频转录或文稿片段；如果为了顺滑而删掉例子、原因链、限定条件、反复强调、转折、比较对象或未完全确定的表达，应回到源片段恢复。
- 存疑时间戳只能来自 sentence/phrase 级 anchor，或 `source=sensevoice_vad_segment` 且 `duration_ms <= 10000` 的短 VAD segment；其他 segment/chunk/minute 级范围只能作为内部复核线索，不得当作可靠存疑时间戳写入正文或存疑表。
- 音频来源但无可靠时间戳 anchor 时，保留音频来源事实，正文只加粗存疑词、不写时间戳占位，并使用 `--timestamp-mode unavailable` 校验无时间戳表格路径。
- 存疑词反查必须基于同一份 `doubtful_items` 清单，先匹配 `timestamp_index.text`，再派生正文 inline 时间戳和存疑表时间戳列；没有可靠锚点时使用无时间戳表格，不写 `未提供`。
- 公司全称、简称、ticker、英文缩写和行业术语要结合上下文、代码资源和外部证据核验。
- 不因外部资料更完整就覆盖音频/文稿中的明确不确定表达。
- 纯人名或普通发言人标签不确定时可忽略，除非身份改变投资事实、标的归因或 source credibility。
- 不用公开资料补写原文没有的客户名、订单额、业绩预测。
- 不把传闻、小作文、未公开客户名写成确定事实。

## 标的归因

推荐标的、比较标的、客户、供应商、竞争对手、上下游、产业背景和偶然提及对象要区分处理。这里的区分依赖语言模型结合上下文做语义判断，不依赖正则、固定关键词或动作映射。

核心规则：
- 最先提到或频次最高的标的不自动等于主标的或推荐标的。
- 客户、供应商、竞争对手、可比公司、上下游实体、产业背景和偶然提及对象不得提升为多人复盘会标的行。
- 外部资料只用于确认名称、代码、简称、术语和公开事实，不得把会议材料没有出现的公司补进标的行。
- 标的行只能写证券标的和代码，不能写方向、板块或主题。
- 多人复盘会中，只有当前段落明确看好的证券标的才进入标的行；看空、回避、减仓或谨慎对象在正文中保留，不进入标的行。
- 同一板块、同一主题、同一逻辑链下的多个明确看好标的可以共用一个标的行；主题或逻辑链不同的个股必须拆成独立 `#### 【...】` 段落。
- 同一主题中同时出现看好和看空对象时，可以不拆段，但标的行只记录看好标的。
- `ticker_status` 非 confirmed 时不得进入标题或标的行；如需保留候选，只能作为正文存疑片段和存疑表处理。

终稿前使用模型做一次语义审查：

```text
请基于当前会议材料审查多人复盘会正文标题和标的归因，不使用关键词或正则作为判断依据。

逐段检查：
1. 每个 `#### 【板块｜细分板块】` 是否是独立主题、逻辑链或明确比较组；不相关主题是否被错误合并。
2. `##### 【标的(代码)】` 是否只包含证券标的和代码，是否误写了方向、板块或主题。
3. 标的行中的证券是否都是当前段落明确看好的对象；是否混入看空、回避、减仓、顺带提及、客户、供应商、竞争对手、可比公司、上下游或背景对象。
4. 是否漏掉同一主题中明确看好的主要标的。
5. 是否出现会议材料没有提到、仅由外部资料或整理者补充出来的公司。
6. 多个股票共用一个标的行时，是否确实共享同一板块、主题和逻辑链；不共享时应拆段。

发现问题时，直接修正 Markdown 的分段、板块行、标的行和正文衔接，再进入结构校验。
```
