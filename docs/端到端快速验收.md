# 端到端快速验收

本验收使用仓库内的合成示例，不需要任何历史会议或内部数据库。

## 前置检查

```bash
python3 -B -m unittest discover -s .implementation/meeting-pipeline-contract/tests -p 'test_*.py'
python3 -B -m unittest discover -s .implementation/meeting-pipeline-worker/tests -p 'test_*.py'
python3 -B -m unittest discover -s .implementation/meeting-pipeline-ops/tests -p 'test_*.py'
```

确认飞书应用已发布 `drive.file.bitable_record_changed_v1` 和 `drive.file.created_in_folder_v1` 两个事件；Router 日志已显示长连接启动；Worker 的 `check` 通过；并且 Worker 使用的 generation、review、receipt 目录与 Router 容器挂载的 `data` 目录对应同一份宿主机字节目录。

## 提交测试纪要

在测试 Base 的表单或表格中新建记录：

- 会议日期：`2032-07-06`；
- 会议系列：任意测试单选值；
- 会议类型：任意测试单选值；
- 会议纪要上传附件：仓库文件 `.implementation/meeting-minutes-structured-table/sample_minutes.md`。

该文件中的公司、代码、日期和发言人均为合成示例。

## 预期过程

1. 上传附件触发 Base 记录变更事件；Router 自动生成 `会议ID`，创建或更新源纪要链接，将三个审核状态置为 `未审核`，并写入两条生成任务。验收时不得调用手工补跑入口代替这一步。
2. Worker 分别生成 `行业与市场观点MD` 和 `标的观点MD`；两个分支独立完成，不互相阻塞。
3. 人工打开源纪要和两类观点 Markdown 校对，把相应审核字段改为 `已审核`。
4. Worker 从当前审核后 Markdown 生成正式 JSON，写入对应 JSON 字段，并在 Drive 保存审核前、审核后和历史版本。
5. 再次提交同一事件或重复点击审核，不得产生重复权威文件或重复 Base 记录。

## 通过标准

- Base 中只有一条对应会议记录，`会议ID` 稳定且 `数据版本` 单调递增；
- 两类观点 Markdown 均能打开并保留原文证据；
- 审核后 JSON 来自当前 Markdown，而不是旧草稿；
- Base 链接指向当前权威版本，旧版本仍可在 Drive 历史目录追溯；
- Router/Worker 日志不出现权限、字段绑定、资产哈希或任务队列错误；
- 五条 Workflow 在列表中均显示“已启用”，至少一次收到上传、待审核和结果完成通知；
- `.env`、字段绑定、token、日志、回执和测试产物均未进入 Git。

## 重启与漏事件验收

1. 确认 Router、Worker 和 Reconciler 已交给 systemd 或等价服务管理器托管。
2. 重启部署主机；Windows + WSL2 还要确认发行版已由登录任务启动。
3. 不手工运行任何启动命令，检查三个服务均为 active，再上传一份新的合成纪要。
4. 在服务短暂停止期间向测试 Base 上传一份合成附件，恢复服务后确认 Reconciler 在下一轮扫描中自动生成会议ID并进入双路任务。
5. 若会议ID仍为空，检查补偿器候选数、Router 的 `FEISHU_FORM_INGRESS_ENABLED`/`FEISHU_DRY_RUN`，以及应用事件是否随已发布版本生效；不得用手工补跑掩盖验收失败。
